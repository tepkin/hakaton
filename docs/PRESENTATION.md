# GreenPlan AI
**Сервис автоматического проектирования озеленения города
с учётом подземных коммуникаций и городской среды**

Кейс ДПиООС Москвы · Хакатон 2026 · команда [название]
Репозиторий: github.com/tepkin/hakaton · Docker · полностью офлайн

## Проблема: рутина, человеческий фактор, риск

- **Дни ручного труда** на участок: открыть подоснову, сверить нормы, расставить «на глаз», перепроверить
- **Не масштабируется**: десятки участков пилота «20 улиц» одновременно
- **Цена ошибки**: посадка над трубопроводом = повреждение сети + отказ в согласовании

<!-- Сегодня проектировщик держит в голове три нормативных акта и расставляет деревья фактически вручную. Это дни работы, зависимость от опыта и риск, который материализуется в повреждённых сетях и отказах. -->

## Решение одной фразой

**DXF/DWG вход → нормы и зоны → план посадок →
DXF-результат на отдельном слое + интерпретации по каждой точке**

- веб-интерфейс 5 шагов (не обязателен: есть CLI и Docker)
- результат открывается в nanoCAD/AutoCAD как родные слои
- обучаемое распознавание слоёв с подтверждениями эксперта

## Архитектура решения

~~~
DXF/DWG -> [Импорт: ezdxf + LibreDWG, кэш по hash]
        -> [Распознаватель слоёв: токены + блоки + геометрия + профили]
        -> [Нормативный движок: буферы СП/743-ПП/623-ПП -> зоны]
        -> [Генератор: воспроизводимая расстановка (seed), виды по территории]
        -> [Бюджет: ТСН/вручную; политики warn | optimize | strict]
        -> [Интерпретатор: точка -> препятствие -> норма -> пункт НПА]
        -> [Экспорт: слои GREEN_AI_* + interpretation/estimate/summary]
Обвязка: CLI, Web 5 шагов, FastAPI + Swagger /docs, Docker, portable
Данные: norms.json, costs.json, plant_catalog.json, layer_knowledge.json (без СУБД)
~~~

<!-- Семь ядерных модулей, каждый отвечает за свою стадию. Вокруг — три способа взаимодействия и Docker. Осознанно без базы данных: только JSON-конфиги, это даёт переносимость, воспроизводимость и отсутствие лишних сущностей в контуре заказчика. -->

## Алгоритм: семь стадий (главный акцент)

1. **Импорт и распознавание слоёв** (уникальные имена — не помеха)
2. **Нормативные буферы** вокруг сетей, дорог, зданий, снегоскладов
3. **Допустимые / запрещённые зоны** = участок минус буферы
4. **Подбор видов** из московского ассортимента под тип территории
5. **Расстановка и проверка каждой точки** по всем нормам (seed-воспроизводимо)
6. **Контроль бюджета** по выбранной политике
7. **Интерпретации и экспорт** в DXF + JSON

Схема процесса: `docs/BPMN.md` (BPMN-эквивалент)

<!-- Вот сердце продукта. Ни одна точка не попадает в чертёж непроверенной: сначала зоны, потом кандидаты, потом пофайловая проверка каждой точки, и только затем экспорт. Схема процесса лежит в документации в формате BPMN. -->

## Нормативное ядро

| НПА | Что задаёт | Пример пункта |
|---|---|---|
| СП 42.13330.2016 | отступы от дорог и сооружений | п. 9.3: деревья ≥ 5 м, кустарники ≥ 3 м от края проезжей части |
| 743-ПП | охрана подземных коммуникаций | прил. 3, табл. 2: водопровод ≥ 2 м (деревья), ≥ 1 м (кустарники) |
| 623-ПП / МГСН | городские требования к размещению и согласованию | отступы от зданий, окон, снегоскладов |

Нормы зашиты как **машиночитаемые правила с точными ссылками**;
добавление новой нормы = правка `data/norms.json` без изменения кода.

<!-- Нормы у нас не в головах и не в PDF, а в исполняемых правилах с точными ссылками на акт и пункт. Заказчик может вести нормативную базу сам: добавить норму — это правка JSON-конфига, код не трогается. -->

## Организация слоёв DXF

**Исходные слои не изменяются и не перезаписываются.**
Результат живёт на отдельных слоях, включаемых независимо:

- `GREEN_AI_TREES` — предложенные деревья
- `GREEN_AI_SHRUBS` — предложенные кустарники
- `GREEN_AI_ZONES_ALLOWED` — допустимые зоны
- `GREEN_AI_ZONES_FORBIDDEN` — запрещённые зоны (буферы НПА)

Проверка в nanoCAD: исходные сущности послойно идентичны входу
(автоматический тест сравнивает имена слоёв и число сущностей).

## Уникальные чертежи: обучаемое распознавание слоёв

- имена слоёв пишут люди: «Дендра_сохранить», «04 Посадки (привязки)», «0 Хранение снега»

## Бюджет и политики

- лимит: **ТСН на гектар** / вручную / без лимита
- политики: **предупреждать**, **автоподбор** (снимает дорогие посадки до входа в лимит), **блокировать**
- блокировка = понятная карточка с рекомендацией, а не сырая ошибка
- смета: типовые цены + компенсационные мероприятия, `estimate.json`

![bg right:33%](screens/budget_block.png)

<!-- План озеленения — это ещё и деньги. Смета считается по типовым ценам и нормативу ТСН, а поведение при превышении задаётся политикой: предупредить, автоподобрать или жёстко заблокировать расчёт с понятной карточкой. -->

## Воспроизводимость и самоконтроль

- **seed**: один вход + одно зерно = байт-в-байт одинаковый результат (тест детерминизма)
- **самоконтроль**: одобренная точка не остаётся в запрещённой зоне и на инфраструктуре; счётчик нарушений в `summary.json` = 0
- **тесты**: pytest (нормы, генерация, пайплайн) + `audit_full.py` (структура, маркеры, e2e, DXF-сравнение, сервер, Docker)
- обучение базы знаний **не мутирует** между прогонами (только подтверждения человека)

<!-- Мы лечили нестабильность системно: автообучение выключено по умолчанию, добавлен пост-контроль норм и тест детерминизма. Три прогона одного файла дают идентичные интерпретации — это проверяется автоматически. -->

## Техническая суть решения

**Обоснованный гибрид, а не витрина:**

- **детерминированное ядро**: вычислительная геометрия (буферы, зоны, воспроизводимая расстановка), нормы как данные, пофайловая проверка точек
- **объяснимое ML**: классификация слоёв по токенам/примерам/геометрии с human-in-the-loop; нейросеть в ядре сознательно не используется — ТЗ требует проверяемости по пункту НПА
- **трассировка**: «посадка → препятствие → норма → пункт НПА» в interpretation.json
- **инфраструктура**: Docker (ТЗ), Swagger, тесты, аудит-скрипт, офлайн-дистрибутивы

<!-- Техническая суть — гибрид: нормативная часть детерминированная и проверяемая, машинное обучение там, где оно нужно и остаётся объяснимым. Мы сознательно не прятали логику в нейросеть: ТЗ требует проверяемости каждого решения по пункту НПА, и ядро даёт её по построению. -->

## Ограничения и идеи масштабирования

**Честные границы:**
- нет слоя границы → участок = выпуклая оболочка (с предупреждением пользователю)
- экзотические версии DWG → результат отдельным DXF с понятной пометкой
- фотореалистичные визуализации — следующий шаг (бонус-трек)

**Масштабирование и внедрение:**
- пакетный прогон всех улиц пилота; REST/Swagger для интеграции с ГИС ДПиООС
- профили распознавания между объектами; новые НПА без кода
- Kubernetes — опционально (ТЗ не требует); пилот на ресурсах ДПиООС

<!-- Мы честны в границах: если слоя границы нет, говорим об этом прямо; экзотический DWG не портим молча, а выдаём пометку. Масштабируется решение естественно: пакетные прогоны, REST для ГИС, накопление профилей между объектами. -->
